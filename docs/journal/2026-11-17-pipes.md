# Pipes and redirection

What it means at the prompt:

    dir > list.txt             what dir says goes into a file
    echo more >> list.txt      added to the end of the file
    wc -l < list.txt           the file is the command's input
    type notes.txt | find "milk" | more

## 2. What was found

- The shell's commands are functions, run one at a time by the session on
  the session's one task. A command is not a process and has no task.
- Every command writes through `Session::write()`, and errors through
  `Session::fail()`. No command read any input.
- There was nothing to put on the right of a pipe: no `more`, no `grep`.
  A pipe without filters does nothing, so they are part of this item.
- Text has two forms in this OS: UTF-8 on the terminal, Latin-1 in files
  (the Editor's form).

## 3. The options, and what was chosen

### What a pipe is

- **A hidden file, one command after the other (chosen): the MS-DOS way.**
  `A | B` runs A to its end with its output in a temporary file, then runs
  B with that file as its input, then deletes the file. It needs nothing
  the shell does not have, costs no memory beyond a 256-byte buffer, and
  whatever the size of what A writes, it fits if the disk has room. What it
  cannot do is run both at once: `B` sees nothing until `A` has finished,
  so a command that never ends cannot feed a pipe. No such command exists
  here yet.
- Real pipes: each command on a task of its own, a buffer between them, the
  writer sleeping when it is full. The Unix way and the right one for
  programs that run for ever (`tail -f`, a log viewer). It needs a task and
  a stack per command and commands that are safe to run side by side. A
  later step if such programs come; the commands would not change, since
  they already only read input and write output.
- A buffer in memory, one command after the other. Faster than a file for
  small outputs, but it has a size, and `type big.txt | find x` would have
  to fail or fall back to the file anyway.

The two files are `.~pipeNa.tmp` and `.~pipeNb.tmp` in the root of the drive
the session is on, N being the session's number, so two Terminals do not
share them. They are used in turn along the line and removed at its end.
Names that start with a dot are hidden from `ls` and the File manager.

### Where errors go

- **Always to the terminal (chosen).** `type nothing.txt > out.txt` says
  "not found" on the screen and leaves `out.txt` empty, as on Unix, where
  errors have a channel of their own.
- Into the file with the rest, as on DOS. Simpler, and the reason people
  open a file and find an error message in it.

There is no `2>`: nothing asked for it.

### Latin-1 and UTF-8

A redirected command writes a file, and files hold Latin-1; the same
command on the terminal writes UTF-8. So the session converts when the
output is a file: text a command prints (a file name with an accent, from
`dir`) becomes Latin-1, and the bytes of a file being shown (`type`) go
through as they are. Input the other way: a file is read as it is, typed
lines are turned into Latin-1. The filters work in Latin-1, so `find` with
an accent in the text finds it in a file the Editor saved, in either case
with `-i`.

### Which filters

Chosen: the ones a pipe is used with every day, with their Linux names and
the DOS name where there is one.

| Command | Does |
|---|---|
| `more` | a screen at a time: Space for the next, Enter for one line, q to stop |
| `grep`, `find`, `findstr` | the lines that have a text; `-i -v -n -c` |
| `head`, `tail` | the first or last lines; `-n N` |
| `wc` | lines, words, bytes; `-l -w -c` |
| `cat`, `type` without a file | the input, as it is |

- `grep` looks for plain text, not patterns. A pattern matcher is a small
  program of its own, and DOS's `find` never had one.
- `tail` keeps the last 2 KB of its input as it goes by, so it shows "the
  last N lines, 2 KB of them at most". Reading the input twice would lift
  the limit for files, not for the keyboard.
- `sort` is left out. Sorting needs the whole input in memory, or a merge
  on disk; `dir | sort` is the one everybody remembers and `dir` is sorted
  already. Listed as left.
- `ls` into a file or a pipe writes one name on each line, as on Unix.

### Input from the keyboard

`cat > notes.txt` and then typing, until Ctrl+D, is how a file is made at a
prompt. It needs the session to sleep until a line is typed, which it can
do on a task of its own (the Terminal on the board, the PC console) and
cannot on the UI task (the Terminal in the browser). There, a command with
no file and no pipe says what it needs instead of waiting for ever, and
`more` shows everything at once.

### Limits written into the code

Six commands on a line. `<` only on the first and `>` only on the last. No
`2>`, no `&&`, no `;`, no variables: none of them were asked for.

## 4. What was built

- `core/src/sh/sh.cpp`: `execute()` cuts the line at each `|` outside
  quotes and runs the stages in turn; `run_stage()` takes `<`, `>` and `>>`
  out of a stage (anywhere on it, with or without spaces, quoted names),
  opens the files, runs the command and puts things back; `write()` goes to
  the file when there is one; `read_input()` is the command's input;
  `fail()` always writes to the terminal.
- `core/src/sh/filters.cpp`: the five filters, over a small `Source` that
  reads a named file or the session's input, a line or a block at a time.
- `tty::Tty::can_wait()`.
- The PC console program at the end of piped input now sends Ctrl+D for as
  long as something still reads, so `cat | wc` in a script ends.
- Tests in `host/tests/test_sh.cpp`: `test_pipes` (every form of
  redirection, quoting, Latin-1 both ways, each filter and its options,
  pipes of two to four commands, every refusal, nothing left behind), and,
  on real threads, typing into `cat | wc` and `cat > file`, Ctrl+C in the
  middle of it, and `more` stopping at each screen and taking Space, Enter
  and q.
- The help screen's reference picture changed (five more commands and a
  line about `|`); the list no longer fits on one screen.
- 29 PC tests pass; the shell test ran 40 times in a row. The firmware
  compiles and links (the board's compiler found a `%s` that could be
  given nothing, as it did once before). **Not run on the board.**
