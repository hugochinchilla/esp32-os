# Telnet: the command shell over the network

2026-11-17. Backlog item 17.

## What was asked

"Telnet server, no password. Ask the owner first: on by default, or switched
on in a settings file." The owner had already said that there are no users
and no passwords in this system (2026-11-16), and that the shell must be the
same program whether the other end is the serial port, a telnet connection
or a terminal window.

## What was found

- The pieces were all there. A session (`sh::Session`) talks to a TTY and
  knows nothing about what is behind it; the Terminal window is one user of
  it. The services loop (`inetd`) already carries VNC and the web viewer on
  one task that never waits.
- Two things were missing. A TTY had no way to hold a program back when the
  far end is slow: the Terminal window draws at once, a socket does not
  always take what it is given. And `ted` remembered the screen in the
  session's 2 KB, which is 80 by 25 and no more; a telnet client's window is
  often bigger.
- The owner was away when the item came up, so the question in the backlog
  went to him as a card and the work went ahead on the recommended answer.

## Options

**Is it on when the board starts?**

- *Chosen (to confirm): off, switched on in a settings file.* `[telnet]
  enabled = true` in `C:\.config\network.ini`. A shell with no password that
  can delete files should not appear on a network because the board was
  plugged in; whoever wants it writes one line. The firmware log says so in
  a warning when it is on.
- Not chosen: *on by default.* Nicer for the film (connect and it answers),
  but anyone on the same Wi-Fi gets the shell. One line in a file changes
  it, and the default is the owner's to turn round.
- Not chosen: *not now.* The item is small and everything it needs existed.

**How many sessions.**

- *Chosen: one at a time.* A second caller waits in the listener's queue
  until the first leaves. One session costs 12 KB of stack plus the TTY and
  the session; a table of them is easy later.
- Not chosen: *several.* More memory held for something nobody has asked
  for yet.

**Where the socket work happens.**

- *Chosen: on the services task, never waiting; the session on a task of
  its own.* The service takes the telnet commands out of what arrives and
  gives the rest to the TTY; what the session shows goes into a 2 KB ring
  and the services task sends what the connection will take. The session's
  task starts when someone connects and is given back when they leave.
- Not chosen: *a task that blocks on the socket.* Simpler to write, but it
  is the pattern the services loop was made to remove (item 8b).

**What happens when a program writes faster than the network takes.**

- *Chosen: the program waits.* The TTY now writes in pieces of 256 bytes
  and, before each, asks whoever is behind it whether there is room
  (`Tty::on_room`), with no lock held. Telnet's answer sleeps the session's
  task until the ring has room. 512 bytes are kept back for the echo of
  what is typed, and typed bytes keep being read while output waits, so
  Ctrl+C stops a long listing at once.
- Not chosen: *drop what does not fit.* A `type` of a long file would lose
  lines.
- Not chosen: *a ring as big as the biggest output.* There is no biggest.

**What the client is asked for.**

- Character-at-a-time with our echo (WILL ECHO, WILL SUPPRESS-GO-AHEAD), so
  the TTY's own line editing works as in the Terminal, and its window size
  (DO NAWS), which `ted` and `top` use. Everything else is refused. The
  client's "interrupt process" is Ctrl+C.

## What was built

- `core/net/telnet.hpp`, `core/src/net/telnet.cpp`: `net::Telnet`, a
  service of the services loop. Portable: it sees a listener, a lock, two
  events and a place to get a task from.
- `Tty::on_room` and writing in pieces (`core/tty`).
- `shell::session_environment`: what a session outside a Terminal window
  works with (the drives, the process table, the way to the UI task, the
  time zone, memory charged to its process row).
- `ted` now keeps what it remembers of the screen after the text, in the
  block it already asks for, so it draws up to 160 by 64.
- The board: `telnetd` in the process list when the settings file says so;
  port 23. The simulator: `./sim folder vnc-port web-port telnet-port`.
- `docs/settings.md` has the new key.

## How it was tested

- `host/tests/test_telnet.cpp`, with a connection made of memory whose
  reader can be slowed or stopped: the options offered, the greeting, echo
  a key at a time, the client's window size (100 by 40) and the refusal of
  what we do not do, a long listing arriving whole through a slow reader,
  Ctrl+C and telnet's own interrupt during it, `ted` drawing 40 rows,
  `exit`, the next caller starting afresh, a caller who vanishes in the
  middle of a command, no memory for the session's task, and the service
  taken down with someone connected.
- The simulator, over a real socket: `ver`, `ps` (shows `telnetd` and
  `inetd`) and `dir` answered as in a Terminal.
- All 32 PC tests pass. The firmware compiles and links (0x15b0a0 bytes).
  It has not run on the board.

## On the board (added by the board thread, 2026-11-17)

Branch commit 1d34131 with main e18c324 merged in. The backlog table and the
journal index conflicted; the resolution keeps the board results already on
main and the branch's new lines. PC tests passed (33 of 33) and the firmware
build was clean.

1. With the key absent (no `C:\.config\network.ini`): port 23 refused the
   connection, `ps` had no `telnetd`, and VNC and the web page answered as
   before.
2. With `[telnet] enabled = true` and a restart: port 23 open, and `ps` shows
   `telnetd` (PID 2). From the laptop, with a small client of my own that
   refuses all options but echo and suppress-go-ahead: the greeting and the
   prompt; `dir` (with dates) and `ps` right; `top` refreshed 3 times in 5 s
   and left with q; `ted` as in its own journal.
3. `type` of a 300 KB file with Ctrl+C after 2 s: 157,014 bytes had come
   (about 78 KB/s), it stopped with `^C` and the prompt, and no refill was late
   or missed.
4. `exit` closes the connection. A second connection gets a fresh session.
5. A client killed with SIGKILL while `type` ran: a new connection got a
   prompt at once, and `ps` shows the same three processes.
6. The `inetd` task had 2,392 bytes of its 4 KB stack never used after all
   this.
7. Memory: an open session takes 12,784 bytes of internal RAM and 304 of
   external. After the session: internal back to the byte, external 232 to
   444 bytes lower (the same few hundred bytes the browser viewer leaves). No
   task was left but `ui` and `inetd`.
8. Free internal RAM on an idle desktop: 210,831 bytes with telnet off,
   210,331 with it on (listening), against 211,071 on main e18c324.
9. At the end I deleted `C:\.config\network.ini` (it did not exist before),
   restarted, and port 23 refused again: telnet is back to OFF.

## The owner's answer: on by default (2026-11-17)

The question left open above was put to the owner on a card with two
options: off until a settings file switches it on (recommended, and what
was built), or on by default. He chose on by default. The firmware now
reads `[telnet] enabled` with true as the value when the line is not
there, so a board without the line offers the shell on port 23 from its
next start, and `enabled = false` is how to switch it off. Nothing else
changed: one session at a time, no password, and End Task on `inetd` still
ends it. The simulator is as it was (telnet there is a port given on the
command line).

One line in `firmware/os/main/main.cpp`; the PC tests do not cover that
line. The firmware compiles and links; it has not run on the board. To
check there: with no `[telnet]` section, `telnet <board>` gets a prompt;
with `enabled = false`, port 23 refuses.
