# The OS calls: one door between the programs and the system

2026-11-17. Backlog item 20, first part.

## What was asked

"A defined set of OS calls, moved to app by app." The architecture review
put it this way: programs reach into the window manager, the drives and the
hardware ports through global variables; there should be one defined set of
calls, because that is where accounting per process, kill checks and limits
attach, and because programs that are loaded or boxed in (item 27) need it
first.

## What was found

- The sixteen program files in `core/src/shell` use four accessors:
  `manager()` (the whole window manager), `storage()` (the drives),
  `system_port()` and `proc::table()`. Counted by use, what programs
  actually ask for is little: timers and the clock, files, a window opened
  or brought forward, a frame in the middle of the screen, memory, a process
  for another copy of themselves, a restart.
- A few files ask for much more, and those are the desktop itself or tools
  that are about the system: the Task Manager reads the process list and
  sends signals, Display sets the background, Screen Saver installs the
  screensaver.
- Memory was already asked for in one place (`program_memory`), which notes
  on the process's row what it holds. Timers already belong to the process
  that asked and stop with it. So two of the things the review wanted to
  "attach" were there, only not behind a common door.
- The Editor writes its file from a background job, on another task. "Who is
  asking" is something only the UI task knows today, so anything counted per
  process in the file calls needs the job to say whose it is.

## Options

**What the calls look like.**

- *Chosen: a thin layer in C++*, `core/os/os.hpp`: about thirty functions
  in a namespace `os`, over what exists. Programs keep their window classes
  and widgets. Moving a program is replacing a line at a time, so it can be
  done program by program with the tests passing at every step.
- A C-style interface with numbers and handles (windows, files and timers
  as small integers, events through a queue). It is what loadable programs
  will need in the end, because a program built apart cannot share C++
  classes with the system safely. Not chosen now: every program and every
  widget would have to be rewritten against it before anything worked, and
  the shape of that interface depends on how programs are delivered, which
  is the owner's open question. The thin layer does not close this door:
  the handles can be put behind the same names later.
- Leaving it. Then item 21 (the split of the window manager) has nothing to
  split along.

The owner was asked (a card in the thread) with the first option
recommended; this part was built on it meanwhile and is marked "to
confirm".

**How to keep a moved program moved.**

- *Chosen: a list and a check.* `tools/check_os_calls.py` lists the files
  that have moved and fails, as one of the PC tests, if one of them names
  the window manager, the drives, the System port or the process table. It
  also prints how many are left.
- Taking the accessors out of `internal.hpp`. Right at the end, when every
  program has moved; today nine files still need them.
- A convention in a comment. Conventions without a test did not survive in
  this project before (the journals overwritten by a merge are the proof).

**Files: paths and `fs::File`, or handles owned by the process.**

- *Chosen for now: the same calls as the drives have*, passed through. No
  program keeps a file open across events (the Editor opens, reads and
  closes in one go; a save is one job), so there is nothing to leak today.
- A table of open files per process, closed by the system when the process
  ends, with a limit each. This is the right end state and the first thing
  item 26 (programs on their own tasks) will want. It was left out of this
  part because of what was found above: the save runs on another task, so
  the table needs a lock and the job must say whose it is. Better done as
  its own step than hidden in this one.

**What does not go through the calls.**

- The dialogs any program may open (message box, questions, Open and Save
  As) stay in `shell.hpp`. By the owner's rule they are programs of their
  own; asking for one is starting a program, not a call into the system.
- Widgets and painting stay as they are: C++ classes of `core/wm`.

## What was built

- `core/include/core/os/os.hpp` and `core/src/os/os.cpp`: process (`self`,
  `spawn`, `find`, `As`), time (`now_us`, `start_timer`, `stop_timer`),
  memory (`allocate`, `release`, `memory`, and two counters of what is out),
  windows (`show`, `activate`, `move`, `work_area`, `centred`, `menu_open`,
  `Busy`), files (`os::file::...`), settings and `restart`.
- The memory accounting moved from the desktop into `os::allocate` and
  `os::release`; `program_memory` is now a name for them, so no program
  changed for it.
- The desktop hands the OS what it works with when it starts
  (`os::install`), so the board's main program, the simulator and the PC
  desktop program did not change.
- Seven programs moved: Cactus Patch, Culebra, Defrag, the Editor, Run,
  the settings files and the Trash. Nothing they do changed; the reference
  pictures are the same.
- `tools/check_os_calls.py` and `docs/os-calls.md` (the list of calls, who
  has moved, and how to move a program).

## How it was tested

- `host/tests/test_os.cpp`: memory is counted for whoever asked, also when
  someone else gives it back or the owner has gone first; the file calls,
  a save given up and a save kept; settings; a timer that belongs to a
  process; and every program in the Start menu opened and closed, after
  which the blocks and bytes out are what they were before. That last check
  is new and found nothing: no program leaks.
- The `os_calls` test: 7 of 16 moved, none of them names what it may not.
- All 39 PC tests pass and the reference pictures match. The firmware
  compiles and links (0x1602a0 bytes). It has not run on the board. The PC
  desktop program (SDL) is not built in the cloud.

## What is left

- Nine files to move. Three need new calls first: the process list and
  signals (Task Manager, Terminal, Shut Down), a picture decoder that takes
  the file calls (Picture viewer). Display and Screen Saver set things that
  belong to the desktop and are better moved with item 21.
- Open files per process, with a limit and closed at exit.
- Then the accessors come out of `internal.hpp` and the check is the
  compiler's.
- On the board: nothing new to see. A start, the Editor opening and saving
  a file, a game, the Trash, and the memory column of the Task Manager
  going back to what it was after closing each.

## Second part, the same day: four more programs

The File manager, the file dialogs and the message box, the Picture viewer
and the Task Manager moved: 11 of 16.

What they needed that was not there:

- **The process list and signals** (`process_count`, `process_at`,
  `process`, `alive`, `refresh_figures`, `signal`). The Task Manager reads
  the rows and sends TERM and KILL through the calls now. This is the "kill
  check" place of the review: whether a process may signal another is asked
  in one function. Today the answer is the table's own (protected rows
  refuse); nothing was added, because security is not a goal of this
  system.
- **A few window questions** (`open_menu`, `blocker`, `in_front`,
  `main_window`, `begin_drag`) and **figures** (`stats`, `fact`,
  `busy_us`).
- **The folder list** (`Listing`, shared by the File manager and the file
  dialogs) took the drives as an argument; it asks the file calls itself
  now.
- **The picture decoder** reads the file itself, a piece per timer tick,
  and takes the drives. Options: give it a small reader interface filled in
  by the OS; or hand it the drives through one call. *Chosen: one call*,
  `os::file::storage()`, named for what it is: for library code, passed on
  and not kept. A reader interface is the better shape when files become
  handles owned by the process, and belongs to that step; doing it now
  would be writing it twice.

Five are left, each for a reason written in `docs/os-calls.md`: three are
half settings window, half something the desktop keeps running (Display,
Screen Saver, Network), Shut Down is the desktop's own work, and the
Terminal hands the command shell the drives and the process table whole.
The first four are cut along the line item 21 draws.

Tested: `test_os` also covers the list, a signal to a protected process,
to one that is not there and to a window program (which closes), and the
window questions. All 39 PC tests pass, the pictures match. The firmware compiles and links
(0x1601a0 bytes). It has not run on the board.

## The owner's decision (2026-11-17)

The owner asked what each shape of the calls means, what it costs to build
and to run, and how it compares with systems of the time. What he was
told, in short:

| Shape | To build | To run | Gives | Who did it so |
| --- | --- | --- | --- | --- |
| 1. A thin layer in C++, programs compiled with the system (built) | Done for 11 of 16 programs; about a day for the rest, with item 21 | A function call, nanoseconds; on the board memory was the same to the byte | One place to count and limit; no protection, no loadable programs | Mac OS (1984) and its Toolbox, Windows 3.x, AmigaOS |
| 2. Numbered calls with handles | One to two weeks: every program and widget rewritten, nothing works until all is | A table look-up per call, tens of nanoseconds; a few KB for the tables | The system can close all that a process holds and set real limits; what loadable programs need | Win16 and Win32 (HWND, HANDLE), Unix file descriptors, Amiga libraries, DOS `int 21h` |
| 3. Calls across a protected border | Very large, and in part not possible: the ESP32-S3 has no MMU | About a microsecond a call, hundreds of times the others | Real protection | Unix, Windows NT |

The run-time figures are estimates by order of magnitude, not measured on
the board, except where it says so.

He chose 1 for now, with a new backlog item (37) at the end to look at it
again and take it to 2.
