# Updates over Wi-Fi

2026-11-17. Backlog item 25.

## What was asked

"Updates over Wi-Fi." The owner's flash layout of 2026-11-16 kept the room:
"the app area is 0x10000-0x400000 (3.94 MB, one app now; it can later be
split into two over-the-air update slots of about 1.9 MB without moving
C:)". Today a new version reaches the board through the serial cable.

## What was found

- The image is 1.44 MB. Two slots of 1.94 MB fit in the app area with a
  quarter of each free, and C: stays where it is.
- The code runs from PSRAM since 2026-11-16, so writing the flash does not
  stop the picture: the same reason saving a file does not.
- The services loop takes a new network service without a task of its own.
- ESP-IDF has the pieces: writing an app slot, checking the image, a record
  of which slot starts, and a bootloader that goes back to the old version
  if the new one is not confirmed.

## Options

**Who starts it.**

- *Chosen: the PC sends it.* `tools/ota.py chinchilla.local` connects to
  the board and pushes the image that was just built. One command after a
  build, which is when an update is wanted.
- Not chosen: *the board fetches it from an address* (a command at the
  prompt, a web server on the PC). Two things to run instead of one.
- Not chosen: *a page in the browser to upload it.* Friendlier, more code in
  the web gate, and nobody but the owner updates this board. Can be added
  on top of the same writer.

**What is said on the wire.**

- *Chosen: one line of text, the image, one line back*, on port 3232:
  `UPDATE <bytes> <crc32> [restart]`, `OK`, the bytes, `DONE` or `ERROR
  <why>`. It can be read in a capture and tried with `nc`.
- Not chosen: *HTTP*, for the reason above; *ESP-IDF's own HTTPS updater*,
  which is the fetch model and wants certificates.

**What protects the running system.**

- The image is checked twice: a CRC-32 of everything that arrived against
  what the sender said, then ESP-IDF's own check that it is an app for this
  chip. Only after both does the next start change.
- A sender that goes quiet for 15 seconds, or goes away, is given up and
  the half-written slot is abandoned.
- *Chosen: the new version is on trial for ten seconds.* If it does not get
  that far (it crashes at start, or the watchdog resets it), the bootloader
  starts the old one at the next reset. After ten seconds of the desktop's
  loop running it is confirmed.
- Not chosen: *confirm at once.* A version that crashes at start would then
  need the cable.
- Not chosen: *confirm only when the owner says so.* Safer still, and one
  more thing to forget; the cable is always there for the worst case.

**Is it on?**

- *Chosen (to confirm): off unless `[update] enabled = true` in
  `C:\.config\network.ini`*, like telnet: there are no passwords here by
  the owner's rule, and this port replaces the whole system. A board on the
  owner's bench can leave it on for good.
- Not chosen: *always on.*

## What was built

- `ports::Updater`: begin, write, finish, abandon.
- `core/net/update.hpp`: `net::Update`, a service of the services loop. It
  writes a kilobyte at a time and comes straight back while more is
  waiting.
- `tools/ota.py`: sends the last build or a named image, shows progress,
  `--no-restart` to write it and leave the board running.
- The board: `partitions.csv` has `ota_0`, `ota_1` and `otadata` where
  `factory` was; the bootloader's rollback is on; `OtaUpdater` writes the
  other slot, erasing as it goes; the loop confirms a version on trial
  after ten seconds. Log lines say what happened (`dmesg`).
- The simulator takes a fifth argument, the update port, and keeps the
  image in memory.

## How it was tested

- `host/tests/test_update.cpp`: a whole update; one arriving seven bytes at
  a time with answers leaving a byte at a time; the sender waiting for OK;
  eleven wrong first lines; no room; a changed byte; not an image; a write
  that fails; the sender going away and going quiet, and the next sender
  served; a caller who says nothing.
- `tools/test_ota_sim.py`: the real tool against the simulator: refused
  when it is not an image, 700 KB written and compared, the board still
  answering, a restart, and nobody listening.
- All 37 PC tests pass. The firmware compiles and links with the new table
  (0x15fb20 bytes; 29 % of a slot free). It has not run on the board.

## What is left

- On the board. The first flash with this table must be by cable and whole
  (`idf.py flash` after deleting `sdkconfig`: bootloader, table, `otadata`
  and the app); C: is not touched. Then: switch updates on, `tools/ota.py`
  with the same build, see it restart into the other slot and the log say
  "on trial" and then "confirmed"; the picture during the write; the time
  it takes; a second update back into the first slot; an update while a VNC
  viewer is connected; pull the plug half way and see the old one start.
- To try the way back: send a build that stops at start (`tools/dbg.py
  fault` cannot do this; it needs a build made to fail) and see the old
  version return.
- The desktop does not show that an update is arriving; a notice could.
- The slot is 1.94 MB and the image 1.44 MB: there is room for about a
  third more code before the layout has to be thought about again.


## On the board (added by the board thread, 2026-11-17)

Branch commit 067d05c with main a8a5bc0 merged in (no conflict). PC tests
passed (38 of 38). The firmware was built after deleting `sdkconfig`
(`CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE=y` in the result).

Before the flash: the old and new tables, compared line by line (and the
built `partition-table.bin` read back with `gen_esp32part.py`), give `nvs`
0x9000 + 0x6000, `phy_init` 0xf000 + 0x1000 and `storage` 0x400000 +
0xc00000 in both; only the app area changed, from `factory` 0x10000 +
0x3f0000 to `ota_0` 0x10000, `ota_1` 0x200000 (0x1f0000 each) and `otadata`
0x3f0000 + 0x2000. `idf.py flash` wrote only 0x0 (bootloader), 0x8000 (table),
0x10000 (app) and 0x3f0000 (otadata); nothing was erased. A listing of C:
with a CRC of every file (25 entries) was taken before.

1. After the cable flash: C: identical, file for file and CRC for CRC. Wi-Fi
   joined without asking for the password. Everything started as before.
2. Port 3232 refused with no `[update]` in network.ini. With `[update]
   enabled = true` and a restart, it was open.
3. `tools/ota.py chinchilla.local` with the same build, 1,443,216 bytes:
   18.4 s (76 KB/s). The screen shows nothing of it while it writes (a
   screenshot and the webcam mid-write show the plain desktop). No late or
   missed refill. After a restart: "Loaded app from partition at offset
   0x200000" (ota_1), "this version arrived over the network and is on trial
   for 10 s", and 10 s later "this version is confirmed".
4. A second update, with a VNC viewer connected and asking for frames
   during it: 36.7 s (38 KB/s), the viewer kept working, no refill missed,
   and it started from 0x10000 (ota_0), on trial and then confirmed.
5. Cut short: `ota.py` killed with SIGKILL at 15 %, and the board reset
   with its EN pin at 19 % (ota.py: "update failed: the board hung up"). Both
   times the next start was the old version from 0x10000.
6. A damaged image (100 bytes changed in the middle of the file): refused
   at the end with "it is not an image this machine can start". The old
   version started. This damages the file before it is sent, so the
   transfer's own CRC matches and it is the image check that refuses. Damage
   on the way could not be arranged, so the transfer CRC refusing it is not
   tested.
7. Rollback: a test build (a separate worktree, not committed) that hangs
   in the UI loop as soon as it sees it is on trial. Sent with `ota.py` and
   started: it loaded from 0x200000, logged "TEST BUILD: hanging on purpose",
   our watchdog restarted it after 15 s, and the bootloader started the
   previous version from 0x10000. The error screen named the hang; the
   desktop followed. During the error screen ESP-IDF's task watchdog warned
   about IDLE0 several times, the known busy wait of the start-up screens
   (queued on main).
8. The image is 0x160590 bytes (1.38 MB) for a 0x1f0000 slot (1.94 MB):
   29 % free.
9. Free internal RAM on an idle desktop: 209,175 bytes against 210,111 on
   main a8a5bc0 (0.9 KB less), external 6,470,688 against 6,474,792 (4.1 KB
   less). No late or missed refill in 60 s idle.
10. At the end `C:\.config\network.ini` (which did not exist before this
    turn) was deleted and the board restarted: port 3232 and port 23 refuse,
    so updates and telnet are OFF. C: matches the first listing apart from
    crash.txt, which grew with the reports of these tests.

**How to flash from now on.** By cable, `idf.py -p /dev/ttyACM0 flash` as
before. It writes the app into ota_0 and resets otadata, so the board starts
the cable version even if an update had put another one in ota_1. After a
change to `sdkconfig.defaults` or `partitions.csv`, delete `sdkconfig` first.
Over the network, `[update] enabled = true` in C:\.config\network.ini and a
restart, then `tools/ota.py chinchilla.local` (the last build) and a restart.
Never `erase_flash`: it would wipe the Wi-Fi settings and C:.
