# Background jobs, and a save that does not stop the desktop

Backlog item 10. Branch `claude/project-thread-8q7ksu`, on top of the TTY,
the shell and the Terminal window.

## 1. What was asked

The architecture review of 2026-11-16 decided how a save should work, and
the owner asked for the hourglass himself:

> **Saves**: written by a job on a worker task that belongs to the program;
> the program cannot end until its jobs have. The window is locked while it
> saves and the pointer shows an hourglass.

The backlog line is "Jobs owned by a process, and 'cannot exit until jobs
finish'. The Editor saves through a job, its window locked meanwhile". The
owner's standing instruction for this run of work is "ve haciendo, no pares
hasta terminar el backlog, dejo a tu criterio el orden de las tareas", so the
choices below were made by the agent and are marked "to confirm" in
`docs/DECISIONS.md`.

## 2. What was found

- Until now the Editor wrote the file from inside the menu action. The UI
  task did nothing else until the last byte was on the disk: no pointer
  movement was lost (the pointer is mixed in by the video task) but no
  window could be moved, no clock ticked, and a 500 KB save on the board
  takes seconds. The hourglass (`wm::Wait`) was the honest sign of that.
- Everything a job needs was already there except the job: the message
  queue into the UI task (item 8) to bring a result back, the lock on
  `fs::Storage` (item 9) so two tasks can use the disk, and the process
  table (item 2) to say whose the job is.
- The portable core had no way to start a task. The TTY brought a way to
  sleep (`ports::Event`), not a way to run.
- The window manager ends a process in two places: a KILL, and a window
  program whose last window has closed. Both destroy the window objects at
  the safe point, and the Editor's text lives in memory the window gives
  back in its destructor. A job still writing that text to the disk would be
  reading freed memory.

## 3. The options, and what was chosen

### A task per job, or workers that wait for work

- **A task per job (chosen).** The task is made when the job starts and is
  gone when the work returns. Nothing is spent while no job runs, which on
  this machine is nearly always: a stack for a file system call is 6 to 8 KB
  of internal RAM, the scarce kind. Making a task costs well under a
  millisecond, nothing beside a save.
- One worker task, always there, with a queue of jobs. Simpler to reason
  about (one thing at a time) but it holds its stack for ever, and a long
  job, like a shell session that lasts as long as its window, would block
  every save behind it.
- A pool of workers. The cost of both.

### Who owns the count

The rule "cannot end until its jobs have" needs someone to know how many jobs
a process has, and the window manager is the one that ends processes.

- **A count on the process's row (chosen)**: `proc::Process::jobs`, moved by
  the job runner. The window manager only reads a number from the table it
  already reads; it does not know what a job is.
- The window manager asks the job runner. It would then depend on the job
  module for one question.

### What "cannot end" means, exactly

- **KILL waits (chosen).** A KILL sent to a process with a job running stays
  on its row. The job is told to stop (it can ask `stopping()`, and it can
  give a function that wakes it), and when it has returned and its result
  has been delivered, the KILL takes effect at the next safe point. This is
  the "never while the task holds an OS lock" of the signals decision, by
  the simplest means: the task is never taken away at all, it is waited for.
  The Editor's save does not look at `stopping()`: a save half written and
  abandoned would be worse than a second's wait, and the temporary file
  makes it safe either way.
- KILL deletes the job's task. FreeRTOS can do it, and whatever the task
  held (the file system's lock, an open file) would be held for ever.
- **A window program that has closed its last window stays in the table**
  until its jobs are done, and **its closed windows are not destroyed**
  until then. Nothing in the Editor needs this today, since its window is
  locked and cannot close, but a program that closes itself while a job is
  finishing (the Terminal, when its session becomes a job) must not have its
  memory pulled from under the job.
- TERM is not held back by the rule: it asks, and a locked window is simply
  not asked (below).

### The locked window

- **A lock the window manager enforces (chosen)**: `Window::set_locked()`.
  A locked window is painted as usual and can be moved, sized, minimised and
  maximised, since those only read what the program holds. It gets no keys,
  no typed text, no clicks in its client area or its menu bar, no right
  click, no dropped file, and no request to close: not from its close
  button, Alt+F4, End Task's polite try or Shut Down (which is called off,
  as it is for a window with a dialog open). Over it the pointer is the
  hourglass; beside it, the arrow. The program writes one line to lock and
  one to unlock, and cannot forget a case.
- The Editor refuses things itself with a "saving" flag checked in every
  action. Each program would write the same list of checks, and miss one.
- A modal "Saving..." dialog. It locks by the means that exist already, but
  it flashes up and away on every quick save, and the owner asked for an
  hourglass.
- Nothing shows that the window is locked except the pointer. A greyed
  title or a "Saving..." in it was considered and left for the owner to ask
  for: on the board a typical save is short.

### Typing during a save

Decided on 2026-11-16 and not reopened: the job would need a copy of the
text (up to 512 KB more) for the user to go on typing. The window is locked
instead.

### A machine without tasks

The browser build has no threads, and the plain PC desktop and most tests
have no reason to start any. There the job runner has no `ports::Tasks`,
and `start()` does the work itself and calls `done` before returning: the
old behaviour, through the new code. The Editor keeps the whole-desktop
hourglass around `start()` for that case; with tasks it is up for a moment
only.

## 4. What was built

- `ports::Tasks` (`core/include/core/ports.hpp`): "run this function on a
  new task". Adapters: `RtosTasks` (`firmware/os/main/rtos_tasks.hpp`,
  `xTaskCreate` at priority 4, one below the UI task) and
  `host::ThreadTasks` for the tests, which can hold the tasks back and let
  them go so a test can look at every moment of a job's life.
- `core/job/` (`job::Jobs`, `job::jobs()`): `start(spec)` for the current
  process, with `work` (on the job's task), `done` (on the UI task, as the
  owner, with the work's result) and an optional `stop`. Eight jobs at most
  in the machine. The result comes back as a message to the OS through the
  UI queue, waiting for room as long as it takes, because a lost result
  would leave a process that can never end.
- `proc::Table`: the count on the row (`job_started`, `job_finished`,
  `jobs`), and `signal()` tells the job runner when a KILL arrives for a
  process with jobs. A process with a KILL waiting cannot start more.
- `wm::Wm`: a KILL stays on the row while the count is not zero; a window
  program without windows is not removed while it has jobs; closed windows
  of such a process are kept for a later safe point; the lock, in every
  place a window receives something.
- The Editor (`core/src/shell/editor.cpp`): `save()` locks the window and
  starts the job; `write_out()` is the old loop, on the job's task;
  `saved()` unlocks, reports an error or clears the star, and goes on to
  what was waiting for the save (New, Open, Exit).
- Tests, `host/tests/test_job.cpp`, with real threads: the runner with and
  without tasks, `done` starting another job, KILL telling the job once,
  too many jobs, a task that cannot be made, an owner that is gone; the
  window manager's rules with a job counted on the row; every way into a
  locked window; and the Editor end to end: a save held back (locked, old
  file still on disk, a second Editor in use meanwhile), the result
  delivered, "save changes? Yes" on close, End Task with force during a save
  (the file is whole, then the Editor goes, and its memory comes back), and
  a save that fails. The rule was taken out once to see the tests fail (they
  stop on a use of freed memory).
- 29 PC tests pass. The firmware compiles and links in the cloud with
  ESP-IDF v5.5. **It has not run on the board.**

## 5. What to look at on the board

- A save of a large file (300 KB or more): the hourglass over the Editor
  only, another window dragged about meanwhile, the clock ticking, the
  Editor refusing keys and its close button, and the star gone at the end.
- The job's stack: 8192 bytes are asked for the save. The task is gone when
  the save ends, so its high-water mark has to be read while it runs
  (`tools/dbg.py tasks` during a long save) or the size trusted.
- End Task on an Editor that is saving: it should go a moment later, and
  the file should be complete.
