# init: PID 1 and the start-up file

2026-11-17. Backlog item 18.

## What was asked

"init as PID 1 with a start-up file. Services start after the desktop." The
architecture the owner chose on 2026-11-16 says: "init is PID 1 and starts
the rest from a text file". Until now the desktop was PID 1, by the owner's
"make desktop pid 1 for now", with the note that init takes the place when
it is a real program.

## What was found

- The start-up order was written in the firmware's `ui_task`, one block
  after another. The network ports were opened before the desktop and their
  task started after it.
- The process table already treats whoever is made first as the root:
  orphans go to it and a program that comes back is started as its child.
  The desktop asks for its row by name and makes one only if there is none.
  So an `init` row made first takes PID 1 and the desktop becomes PID 2 with
  no change to the desktop.
- One place said "the root" and meant "the desktop": what Start > Run...
  opens was made a child of PID 1.
- The table's note on respawn said "there is no brake on restarting too
  fast (with init, item 18)".
- The owner's rule "only real tasks are listed" asks what the `init` row
  stands for.

## Options

**What init is.**

- *Chosen (to confirm): the UI task's own loop, with a row.* The code that
  runs before any program and between two of them: it reads the start-up
  file, starts what it says, takes in orphans and starts again what must
  come back. No new task. The row is honest in the way a window program's
  row is: something that runs, on the UI task.
- Not chosen: *a task of its own that only sleeps.* The table and the
  windows belong to the UI task, so such a task could do nothing itself; it
  would be a row with 4 KB of stack behind it and no work.
- Not chosen: *no row, the desktop stays PID 1.* Simplest, and against what
  the architecture says.

**The file.**

- *Chosen: `C:\.config\startup.txt`, a line for each thing, two words.*
  `start NAME` for a part of the system (`desktop`, `inetd` today) and
  `run WHAT` for a program or a file, exactly as Start > Run... takes it.
  `#` starts a comment. Order is the file's order. It is with the other
  settings and can be changed with the Editor or `ted`.
- Not chosen: *an .ini file.* The settings files are that, but order is the
  point here and sections with keys hide it.
- Not chosen: *a shell script* run by the command shell (AUTOEXEC.BAT). It
  is the obvious 90s answer and may come: it needs the shell to start parts
  of the system, and a session before there is a terminal.
- Not chosen: *names only, no verbs.* Shorter, but "desktop" and "terminal"
  are different kinds of thing and a wrong name could not be explained.

**When there is no file, or it is wrong.**

- *Chosen: the usual lines are used and the file is written*, after
  everything has started, so there is always one to edit. A line that
  fails is logged and the rest goes on. The desktop is started at the end
  if no line started it: until there is a console to fall back on (item
  14), a machine without it shows nothing.
- Not chosen: *write nothing.* Then the file is something to know about
  rather than something to find.
- Not chosen: *stop at the first wrong line.* A typing mistake would leave
  the machine half started.

**Services after the desktop.**

- *Chosen: the ports open when `inetd` starts*, and the usual file starts
  it after the desktop. Before, the ports opened first; a machine whose
  file leaves `inetd` out now listens to nothing.
- Telnet stays a service inside `inetd`, switched in `network.ini`, as
  inetd's own services are on Unix. It needs the desktop started first.

**The brake on restarts.**

- *Chosen: five quick endings in a row and it is left alone.* A program
  with the respawn flag that ends less than 2 seconds after it started,
  five times one after the other, is not started again, and init logs it.
  One run that lasts starts the count again.
- Not chosen: *wait longer each time.* Kinder, but needs timers in the
  table for something no program does yet (the taskbar, item 21).

## What was built

- `core/init/init.hpp`, `core/src/init/init.cpp`: `init::Init`. The machine
  says what can be started (`add`), how a program is run (`set_run`) and
  where the log goes; `boot()` reads the file a piece at a time.
- `proc::Table`: the brake (`kQuickUs`, `kQuickLimit`, `set_gave_up`,
  `given_up`) and when a row was made.
- Start > Run... makes what it opens a child of the desktop by name, not of
  PID 1.
- The firmware: the desktop and the network services are two things init
  starts; the ports, mDNS, telnet and the services task are in the second.
  The simulator and the PC desktop program the same way.
- The reference pictures with a process list now start with `init` 1 and
  `desktop` 2 (five pictures).
- `docs/settings.md`: the new file.

## How it was tested

- `host/tests/test_init.cpp`: the row; order, comments, case and line ends;
  each kind of wrong line; the desktop started when left out; no file (the
  usual lines, the file written), the file as written, a changed file,
  another path, no drive; the brake (slow endings, five quick ones, another
  program untouched, a long run between quick ones, no clock); and the real
  desktop started by init from a file that also runs a Terminal.
- The simulator: `ps` over telnet shows init 1, desktop 2, and `type` shows
  the file that was written.
- All 33 PC tests pass. The firmware compiles and links (0x15bec0 bytes).
  It has not run on the board.
