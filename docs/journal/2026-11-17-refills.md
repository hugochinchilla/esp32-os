# The missed refills were our own measuring

2026-11-17, the board thread, on `main`.

## What was asked

During the PR 27 board turn the video's refill counters (`refills / late /
missed` in `dbg.py memory`) went up by a few at VNC disconnects. Ten rounds of
connect, one full screen, disconnect gave 3 missed refills at disconnect on
main from before PR 24 as well, so it was older than both. During the PR 26
turn a second finding: `dbg.py tasks` asked every 50 ms for 20 s made the
video miss about a dozen refills on an idle desktop, on main too. The
coordinator asked to find what runs at those moments and fix it if the cause
is ours and the fix is contained; otherwise report options.

## What was found

1. Twenty seconds of each kind of debug request, every 50 ms, on an idle
   desktop:

   | request | requests | late | missed |
   |---|---|---|---|
   | none | 399 | 0 | 0 |
   | ping | 391 | 0 | 0 |
   | stats | 388 | 0 | 0 |
   | windows | 381 | 0 | 0 |
   | memory report | 311 | 15 | 7 |
   | tasks | 361 | 19 | 15 |

   The two that miss refills are the two that list the tasks. Both call
   FreeRTOS's `uxTaskGetSystemState()`: the task list for `tasks`, the
   unused bytes of each stack for the memory report.
2. In ESP-IDF's FreeRTOS on a two-core chip, `uxTaskGetSystemState()` holds
   the kernel's lock (`taskENTER_CRITICAL`, interrupts masked on that core
   and the other core kept out of the kernel) for the whole walk. That walk
   includes counting every task's unused stack bytes one by one. A test
   build timed it: **812 µs for 12 tasks**. The same information for one task
   without counting its stack took 4 µs. A refill is due every 320 µs.
3. Doing the walk on core 0 (`esp_ipc_call_blocking`), away from the video's
   core, did not help: 9 and 15 missed in two 20 s runs. While core 0 holds
   the lock, core 1's own kernel work waits for it (the tick interrupt
   among it). The video's interrupt is allocated by ESP-IDF's RGB panel
   driver at a low or medium level (`ESP_INTR_FLAG_LOWMED`, in
   `esp_lcd_panel_rgb.c`), so it waits behind that. Raising its level would
   mean changing ESP-IDF, which is outside this repository.
4. Every refill check we run reads the counters through the memory report,
   so every reading could itself cause a miss. That is what the "missed at
   disconnect" figures were. With the memory report fixed (below), twenty
   rounds of VNC connect, full screen, disconnect missed **no** refill. Nor
   did a viewer pulling full screens without a pause for 40 s, or ten
   connections opened and closed at once.

## Options

- *Take the stack list out of the memory report (chosen, contained).* The
  same figures are in `dbg.py tasks`. The memory report no longer touches
  the kernel's lock, and the refill counters read through it can be trusted.
- *Walk the tasks on core 0.* Tried, did not help (point 3).
- *Raise the video interrupt's level.* Would need a change inside ESP-IDF.
  Not done.
- *Make `dbg.py tasks` itself cheap.* That needs the task handles without
  `uxTaskGetSystemState()`: a list of handles kept by the firmware (the
  tasks we start, plus ESP-IDF's by name), each read with `vTaskGetInfo()`
  without the stack count and the stack counted outside the lock. It is a
  design change to the System port and was not made: only the debug link asks
  for the task list, nothing a user does reaches it, and the Task Manager and
  `top` do not use it (they missed no refills in their own checks). Left as
  an option for the owner.

## What was built

- `firmware/os/main/main.cpp`: the memory report no longer lists the task
  stacks; it says where they are (`tools/dbg.py tasks`). A comment at
  `tasks()` says what each call costs.
- `tools/dbg.py` and `docs/debug-protocol.md`: the memory report's
  description follows.

## How it was tested

PC tests 40 of 40. On the board, after a flash:

- The memory report asked for 655 times in 40 s: no late or missed refill.
  `dbg.py tasks` the same way still missed 7 in 20 s, as expected.
- Ten rounds of VNC connect, full screen, disconnect, twice: 0 missed while
  connected, 0 at disconnect (one late refill in the second run).
- A VNC viewer taking full screens without pause for 40 s, then
  disconnecting: no late or missed refill. Ten connections closed at once: the
  same.

## What this means for earlier entries

The single missed refills noted "not tied to any one step" in the board
results since PR 22 were read through the memory report. Some or all of them
were probably caused by the reading itself. The PR 27 and PR 24 conclusions
stand: neither added misses.
