# Doom

2026-11-19. Backlog item 81. Built and played on the PC by a test, with the
shareware game data; the program file and the firmware compile and link for
the board. **Nothing here has run on the board**, and nobody has played it
with their hands: the agent cannot. No sound.

## 1. What was asked

The owner, in the project chat, an hour after Bluetooth keyboards and mice
were merged (PR 77):

> pues ahora que tengo teclado y raton solo queda una cosa, JUGAR AL DOOM!!
> habrá que portarlo como app para mi OS

He had it in mind since 2026-11-17: programs became native code loaded from
C: at full speed because "he wants Doom one day"
(`2026-11-17-loaded-programs.md`), and the same day he asked whether a game
with the whole screen could paint its own way, past the window system
(`2026-11-17-program-tasks.md`). The answer then was yes, later.

## 2. What was found

- **A program file may be 1 MB** and is loaded whole into external RAM by
  Espressif's ELF loader. It reaches the system only by name, through a
  table the firmware carries: the OS calls and thirty-odd functions of the
  C library. No `malloc`, no `fopen`, no `printf`.
- **Memory**: 5.2 to 6.2 MB of external RAM are free with the desktop empty
  (`2026-11-18-frame-budget.md`). The game of 1993 ran in a PC of 4 MB.
- **C: is 9 MB.** The shareware `DOOM1.WAD` is 4,196,020 bytes. Freedoom's
  first part is about 28 MB: it does not fit.
- **The picture** is 640x480 or 800x600, one byte a pixel, 3 bits of red,
  3 of green, 2 of blue, no palette. Doom draws 320x200 with a palette of
  256 colours out of 262,144.
- **Programs are called, they do not run**: a program's code is entered for
  an event or a timer and the UI task waits for it (two seconds at most).
  Doom, like every game of its time, is one loop that never returns.
- **Keys**: a window gets a key going down and coming up, but not the
  modifier keys by themselves, which are Doom's fire, run and strafe; and
  Start, Alt+Tab and the menus take theirs first.
- **Sound**: `ports::Sound` plays one recording and a beeper. The board's
  driver plays nothing yet (backlog 58).
- **The screensaver and Shut Down already take the screen away from the
  window manager** (`Wm::hold_screen`, `screen_fn_`): nothing is painted
  and input is dropped until the screen is given back.

## 4. What was built

**The whole screen, lent** (`docs/decisions/lent-screen.md`).
`os::ui::take_screen(window, out)` hands a window the picture's address and
size. While it has it the window manager paints nothing, the pointer is
gone, every key reaches the window as it goes down and comes up (Ctrl,
Shift and Alt too, and nothing repeats), and the mouse comes as movement in
a new event. The loan ends with `give_screen_back`, when the window closes,
when the screen changes size, and on Ctrl+Alt+Del, which then opens the
Task Manager as always. In `core/wm` it is 60 lines on top of
`hold_screen`: one pointer, `lent_`, looked at where keys and the mouse
come in. Two small calls came with it, `os::log` and `os::rest`.

**The program** (`programs/doom`, `docs/decisions/doom.md`), three files of
ours around 70 of the engine's:

- `port.h` is put in front of every file of the engine by the compiler and
  gives the C library's names to functions of ours: `fopen` is
  `port_fopen`, `malloc` is `port_malloc`, `printf` writes lines to the
  system's log. So no file of the engine is changed.
- `port.c` is those functions and the engine's own machine files
  (`i_system`, `i_timer`, `i_video`, `i_input`): the zone of 4 MB, the
  clock, the palette, USB key codes to Doom's.
- `doom.cpp` is the Chinchilla side: a small window, the loan of the
  screen, a timer 35 times a second that runs one round of the engine, and
  the OS calls behind files and memory.

**The loop that never returns** was the easy part: doomgeneric already
splits it into "start" and "one round". What ends a program on a PC,
`exit()` from the Quit menu or from an error, comes back to the timer with
`longjmp`; then everything the engine took is given back from a list, and
an error is shown in a message box.

**The picture**: each pixel of the game becomes four on the screen. Since
there are four, each takes a slightly different rounding of the colour
wanted, from four tables of 256 bytes made when the palette changes: a
dither that costs nothing, and the reds and browns of the game come out
far better than 8 levels would give. A line is put together in fast memory
and copied to the screen whole.

**The build**: `tools/build_programs.sh` compiles the C files a program's
`engine.txt` lists (the engine at `-O2`, without our warnings), and the
firmware's table of exports got `setjmp`, `longjmp` and three helpers.

## 5. How it was tested

On the PC, `doom.app` is built as the PC's kind of program file and loaded
by the test as the board loads it (`host/tests/test_doom.cpp`):

- Without a WAD (as the tests run for everyone): the window says what to
  copy where, takes nothing, and closes clean.
- With `-DDOOM_WAD=.../DOOM1.WAD` (shareware 1.9, MD5
  `f0cefca49926d00903cf57551d901abe`): the title comes up, Escape and
  three Enters start a game, the arrow walks, Ctrl fires, the mouse turns,
  F2 saves a game to `C:\Documents\Doom\doomsav0.dsg`, Ctrl+Alt+Del brings
  the desktop and the Task Manager back, Play goes back into the game,
  Quit Game and Y leave, and all memory and the process are gone. Then
  again, ended from outside in the middle of a level.
- `test_os` got a test of the loan itself, with a window of its own: keys,
  modifiers, no repeat, no Start menu, mouse movement, no screensaver, the
  three ways back.
- All 57 PC tests pass. The firmware compiles and links at 2,306,368 bytes
  (it was about 1.95 MB), of which `doom.app` is 354,316 as carried data;
  all five program files find every name they ask for.

Not tested: anything on the board. How many pictures a second, whether
16 KB of stack is enough, whether 4 MB of zone can be had, whether the
loader takes a file this size, whether the video refill is ever missed
while the game writes the picture.

## 6. What was learned

- **The screensaver started the moment the game was quit.** Giving the
  screen back counts as input "now", but the tick that runs the timers had
  read its "now" before the timer ran, so the idle time came out as a huge
  number. Found by the test's pictures: the desktop was a field of flying
  chinchillas.
- **doomgeneric does not keep settings**, and for a reason: its keys for
  fire and use are not in the table the settings file is written with, so
  a saved file would come back with no fire key. Left off.
- **The engine seeks before every read**, mostly to where it is. Each is a
  call into the system, which costs when the program is late (its start-up
  takes longer than two seconds on the board, surely): the port keeps the
  place and seeks only when it must.
- A program that takes seconds to start is marked "not responding" by the
  system for that long. Nobody sees it here, the screen being lent, but it
  is the next thing the program model does not have a word for.

## 7. What is left

- Sound: a third voice in the Sound port that takes a stream, and a

## 8. The same evening: W, A, S and D

The owner, while the board was running the first checks:

> ok, make wasd move as arrows and q and e strafe

`port.c` hands the engine W, S, A and D as its arrow keys and Q and E as
its keys for a step to the side, beside the keys of 1993, which stay. What
a key types is handed over apart from which key it is, so a saved game can
still be called "W" and the cheat codes still work; for that the engine's
"vanilla keyboard mapping", which took a name's letters from the key, is
off. The cost: in the menus those six letters no longer jump to an entry
(W and S move the skull instead). Not done as key bindings in the game's
settings: the engine has one key for each action, and the settings file
is off. The PC test presses each of the six in a level and names its
saved game "W". Not run on the board.

A minute later:

> while playing, windows key minimizes the game and returns to windows

Read as a request (as built, the logo key went to the game like any other
key, so it cannot have been a report of what he saw). It is the window
manager's, not Doom's, so that every game with the screen gets it: the
logo key ends the loan and minimises the window, and does nothing else,
down or up. Doom's window then waits on the taskbar; its button brings
back the small window, and Play (Enter) the game where it was. Ctrl+Alt+Del
stays. `test_os` and the Doom test check it. `main` was merged in for
this: since backlog item 76 the logo key opens the Start menu when it is
let go, which must not happen after this press, and does not.

## 9. The speed line was ten times too low

The first board turn (batch 26) reported 2.6 to 3.5 pictures a second next
to a round of 20 to 26 ms, and the two cannot both be true: a round of
26 ms is about 35 a second, the engine's own limit. The mistake was in the
log line, which divided the count by 100 where ten seconds ask for 10. So
the board made about 26 to 35 pictures a second in that turn, of which
about 11.6 ms each went to doubling the picture onto the screen. The line
is corrected; the figure itself has not been read again on the board.
