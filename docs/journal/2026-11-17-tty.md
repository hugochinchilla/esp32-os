## 2. What was found

There was no text terminal of any kind. The serial port carries only the
debug protocol's frames. The pieces a TTY needs from the rest of the OS were
there:

- `ports::ByteSink` ("somewhere to send bytes, such as a serial port"), which
  is exactly a terminal's output.
- `ports::Lock`, made for the debug link and used by the file system
  (item 9), for an object two tasks touch.
- Nothing for "sleep until another task has something for me". The message
  queue (item 8) has such a sleep, but it is the UI task's own.
- Fonts with 256 characters, Latin-1. So one byte is one character on the
  screen, and "ñ" is the byte 0xF1.

## 3. What a TTY is

On Unix a TTY is the piece of the kernel between a keyboard-and-screen and a
program. The program does not see keys: it asks for a line and gets it when
Enter is pressed. Until then the line belongs to the TTY, which shows each
character as it is typed (the echo), and lets it be corrected. That is why
`cat` with no arguments has working backspace although `cat` knows nothing
about keys. The TTY also watches for Ctrl+C and turns it into "stop the
program", which is why Ctrl+C works on a program that is not reading at all.

Ours has the same two ends:

```
keys   --> input()  --[ line being typed ]--[ finished lines ]--> read()
screen <-- sink  <------- echo ----------+<--------------------- write()
```

The device end is whoever carries the characters: it calls `input()` with the
bytes typed and is a `ByteSink` for what must be shown. The program end reads
lines and writes text. Neither end knows what the other is, so the same shell
will run on the serial port, on telnet and in a window.

## 4. The options, and what was chosen

### Who edits the line

- **A. The TTY does** (Unix "cooked" mode). The shell asks for a line. Every
  device gets the same editing for free, and any later program that reads a
  line (a `copy con`, a yes/no question) gets it too.
- **B. The shell does** (the way bash does it with readline: the terminal is
  put in raw mode and the shell draws the line itself). Most freedom, for
  example completion that knows the commands. But the editing would live in
  one program, and Ctrl+C would only work while that program is reading.
- **C. The device does** (the terminal window edits the line, the serial port
  relies on the PC's terminal program). Three devices, three behaviours, and
  a plain serial terminal sends each key at once anyway.

Chosen: **A**, which is what the owner asked for by name, with a raw mode kept
for the programs that really want the keys (`top`, the console editor of
item 22).

### How much editing

Unix's cooked mode is poor: backspace, erase the word, erase the line. No
arrow keys and no earlier lines; those come from the shell on Linux. DOS had
them only after loading DOSKEY.

- **A. Only what Unix does.** Smallest (about 150 lines). But the arrows would
  print `^[[D` on the screen, which is what everyone remembers hating.
- **B. Unix's keys, plus the arrows, Home, End, Delete and the last lines
  with up and down, all inside the TTY.** One place, so it works the same on
  every device. Costs about 0.6 KB of RAM per terminal for the earlier lines
  and the draft.
- **C. A hook so the shell can do the rest.** Needed one day for completion
  with Tab, but not for this.

Chosen: **B**. Tab does nothing yet; completing names needs the shell
(item 13) and will come in through a hook.

The keys: Backspace (both codes terminals send, 8 and 127), Left, Right, Home,
End, Delete, Ctrl+A and Ctrl+E (start and end), Ctrl+W (erase the word
before), Ctrl+U (erase to the start), Ctrl+K (erase to the end), Up and Down
(earlier lines), Enter, Ctrl+C, Ctrl+D.

### How the line is redrawn

- **A. With ANSI escape codes** ("erase to end of line", "move left 5").
  Fewer bytes on the wire.
- **B. With characters, spaces and backspaces only.** To erase a character in
  the middle: go back one, write the rest of the line again, write a space
  over what is left, go back to where the cursor belongs.

Chosen: **B**. Every terminal ever made agrees on what a backspace and a space
do, and the terminal window of item 15 can start without understanding a
single escape code. The cost is a few more bytes per key, at 115200 baud.
The known limit: a line longer than the terminal is wide wraps, and a real
terminal's backspace does not go back up over the wrap, so editing the middle
of a very long line looks wrong on the serial port. Our own terminal window
can do better. Lines stop at 159 characters.

### How the program waits for a line

The TTY cannot use threads itself: the core may not include FreeRTOS.

- **A. read() never waits**; the session polls. Wasteful, and a task that
  polls 100 times a second is what item 8 just removed from the UI loop.
- **B. A new port, `ports::Event`**: `set()` and `wait(ms)`. The TTY sets it
  when something arrives and `read()` sleeps on it. On the board it will be a
  binary semaphore, on the PC a condition variable.
- **C. Post a message to the UI queue for every line.** Right for a terminal
  window's program on the UI task, wrong for a shell session, which is a
  task of its own by decision.

Chosen: **B**. With no Event the TTY simply never waits, and with no Lock it
is a plain object, which is how most of the tests use it. The Event is a
general port, since jobs (item 10) will need the same thing.

### What Ctrl+C does

The TTY cannot stop a task. It does three things: throws away the line being
typed and any lines typed ahead (as Unix does), shows `^C`, and raises a flag.
A `read()` answers "interrupted" once; a program that is busy and not reading
looks at `interrupted()` between steps. There is also a function the device's
task calls at that moment, for whoever later turns it into the INT signal of
the process table. The other option, making INT a signal on the process's row
now, touches `proc::Table`, which another branch is changing (item 19); it
belongs with the shell, which is what knows which command is running.

Ctrl+D on an empty line is "end of input", as on Unix: the shell will take it
as `exit`. The device going away (a telnet connection closing) is `hang_up()`:
every later read answers "end", and what is written is dropped.

### Characters

One byte, one character, Latin-1, like the fonts. The other option was UTF-8
inside the TTY, which makes "how many columns is this line" a table lookup
instead of a subtraction. A device that speaks UTF-8 (a modern terminal on
the serial port, a telnet client) converts at its own end: that is a job for
items 14 and 17.

### Text the program writes while a line is being typed

Mixed in, as on Unix. Redrawing the half-typed line after the output would
need the TTY to know the prompt. Left alone.

## 5. What was built

- `core/include/core/tty/tty.hpp`, `core/src/tty/tty.cpp`: `tty::Tty`. No
  heap. One terminal is about 1.2 KB: 160 bytes for the line, 512 for
  finished lines waiting to be read, 384 for earlier lines, 160 for the draft
  kept while walking through them.
- `ports::Event` in `core/include/core/ports.hpp`, and `host::ThreadEvent` in
  `host/host_adapters.hpp` for the tests. The board's adapter (a binary
  semaphore) comes with the first thing that uses a TTY there, so that it is
  not written blind.
- `host/tests/test_tty.cpp`, in `ctest` as `tty`.

How it was tested. The test has a small screen: it understands characters,
backspace, CR and LF, and counts anything else. The TTY's echo is played into
it, and the checks are on what a person would see ("the line reads `cat
file` and the cursor is at column 2") and on what the program reads. It
covers: the five kinds of Enter (CR, LF, CR LF, CR NUL, twice CR), typing
ahead, a read with a small buffer, every editing key, the keys that must
leave no litter (F5, Ctrl+Right, Alt+x), the 159-character limit, Ctrl+C with
a half-typed line and with lines typed ahead, Ctrl+D, hang-up, earlier lines
including the store filling up (13 lines of 28 characters fit in 384 bytes),
echo off, raw mode, and a program that is not reading (the sixth line of 99
characters does not fit in the 512 bytes; Enter rings the bell and works once
there is room).

The last test is the real shape: a session on a thread of its own sleeps in
`read()`, a second thread types 300 lines three bytes at a time with a Ctrl+C
every 50, and the screen must hold nothing but whole typed lines, whole
answers and `^C`. It ran 30 times in a row under the address and
undefined-behaviour checkers. All 24 PC tests pass.

Not tested: anything on the board, and a real terminal program. Both come
with the serial console (item 14).

## 6. What was learned

- The whole of line editing fits in three moves: insert at the cursor, erase
  after the cursor, move the cursor. Backspace is "move left, erase after".
  Ctrl+W, Ctrl+U, Ctrl+K and replacing the line with an earlier one are the
  same two with other numbers.
- "Enter" is five different byte sequences depending on who is typing. The
  rule that covers them: CR and LF are each an Enter, but a LF or a zero
  straight after a CR belongs to that CR.
- Two of the cloud PC tests (`dbg_tool`, `vnc_tool`) fail in a new container
  until `pip install pyserial`. It is not a fault in the code.
