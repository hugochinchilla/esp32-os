# The watchdog, the crash record and the error screen

2026-11-17. Backlog item 7. Built and tested on the PC; the firmware part was
compiled and linked with ESP-IDF v5.5 in the cloud. Nothing here has run on
the board.

## 1. What was asked

The owner, to the coordinator, with the backlog in front of him:

> ve haciendo, no pares hasta terminar el backlog, dejo a tu criterio el orden
> de las tareas y el paralelismo, no tengas más de 4 cosas activas a la vez

Item 7 is one line: "Watchdog, crash record, and an error screen on the next
start". The architecture review (`2026-11-16-architecture-review.md`) had
three things to say about it, and the owner approved all of them:

- "If the UI loop hangs, nothing notices. A tiny high-priority supervisor
  task checks that the UI loop is alive, names the process that was running,
  and restarts."
- "A bad pointer in any app restarts the whole machine. The only trace is
  text on the serial port. Record the crash (which process, where, the call
  chain), restart, and show an error screen on the next start naming the
  culprit. [...] ESP-IDF v5.5's hooks for this were not checked."
- Choice 11, after a crash: "Restart, then an error screen naming the
  program", not a silent restart.

And one sentence from the same review that explains why this is the honest
answer and not a patch: "A window program stuck on the shared UI task cannot
be rescued at all: the honest answer is a watchdog that records the culprit
and restarts the machine."

The coordinator added one condition: do not disturb the video refill or the
Wi-Fi timing. Because the owner asked for the backlog to be worked through
without stopping, the design choices below were made by the agent and are
written down here so he can change any of them.

## 2. What was found

How a hang and a crash went before this change:

- **A hang.** Every program runs on one task, `ui` (priority 5), called by
  the window manager. A program that never returns stops the whole desktop:
  no repaint, no clock, no debug link, no VNC. The video keeps showing the
  last picture, because the picture is sent by an interrupt on the other
  core. Nothing restarted the machine. ESP-IDF's own task watchdog was on,
  with its defaults: it watches the two idle tasks, and after 5 seconds
  without them running it prints a warning on the serial port and carries
  on. So a hang meant a frozen picture until someone pulled the plug.
- **A crash.** A bad pointer, `abort()`, a failed assert or a stack overflow
  goes to ESP-IDF's panic handler, which prints a report on the serial port
  ("Guru Meditation Error", the registers, a backtrace) and restarts. The
  next start looked like any other. Without a serial cable attached at that
  moment, nothing was learned.
- **Who was running.** Since the process table (backlog item 2), the window
  manager records which process it is calling at every moment
  (`proc::table().current()`). That is the name the review asked for; it only
  had to be read at the right moment.
- **The hooks, checked this time.** ESP-IDF v5.5 has no registered callback
  for a panic. What it has: every panic, whatever its cause, ends in one
  function, `esp_panic_handler(panic_info_t *)`, and ESP-IDF itself replaces
  that function in two places with the linker's `--wrap` option (its
  Bluetooth component and its memory-protection tests). By the time it is
  called, ESP-IDF has switched the flash cache back on and armed a hardware
  watchdog over the whole handler. `esp_reset_reason()` says, at the next
  start, how the chip was restarted (panic, interrupt watchdog, brownout and
  so on). And memory marked `RTC_NOINIT_ATTR` is not cleared by a restart.
- **How long the UI task is honestly busy.** The longest stretches measured
  so far: a 300 KB save, up to 3.3 s; a screenshot over the serial link,
  about 3.4 s at worst (300 KB at 921,600 baud). Everything else comes back
  within milliseconds. The loop itself sleeps one second at most.

## 3. The options, and what was chosen

### Who watches

| Option | For | Against |
| --- | --- | --- |
| ESP-IDF's task watchdog, with the UI task added to it and "panic on timeout" switched on | No code of ours; its panic prints the stuck core's backtrace | The same switch makes the idle tasks' 5 s limit fatal too, so any honest busy stretch of 5 s restarts the machine; a settings change for the whole firmware; it names a task, never a program |
| A new small task of our own at high priority | What the review described | A stack in internal RAM (2 to 3 KB) for a few lines of code that run once a second |
| **A callback on the timer task that ESP-IDF already runs** (`esp_timer`, priority 22, core 0) | The same supervisor, with no new task and no new stack. Above every task of ours, so a spinning program cannot starve it | Shares the timer task: a timer callback that never returns would stop the watchdog too |
| The chip's hardware watchdog, fed by the UI loop | Works even if the whole kernel is stuck | It resets the chip with no chance to write down who was running, which is the point of the item |

Chosen: the callback on the timer task. It is the review's "tiny
high-priority supervisor" without paying for a stack; internal RAM is the
scarce thing on this board. Once a second it does a few memory reads and one
comparison, on core 0. The video's interrupt is on core 1 and nothing is
added to it, to the Wi-Fi task or to the network task.

### What it watches

A heartbeat: the UI loop says "I am alive" each time it comes round, and the
supervisor checks how old the last one is.

The other way is to watch for starvation (what ESP-IDF's does with the idle
tasks). It was not taken because it only catches a program that spins. A
program that waits for ever, for a lock that is never released or a reply
that never comes, uses no processor at all and starves nobody. The heartbeat
catches both, and the record says which one it was: "running on core 1" or
"waiting (on no core)".

The bookkeeping is in the portable core (`sys::Watchdog`) and has room for
four watched tasks, not one. Only `ui` is watched today. The shell sessions
and services that the backlog brings can each take a slot.

### How long

| Option | |
| --- | --- |
| 5 s | What Windows waits before it says "not responding". Too close to the 3.3 s save and the 3.4 s screenshot |
| **15 s** | More than four times the longest honest stretch measured. Long enough to see on video that the machine is frozen, short enough not to reach for the plug |
| 30 s or more | Safe, and dull |
| Longer while the hourglass shows | A program that hangs while saving has the hourglass up as well, so it would only delay the answer |

Chosen: 15 seconds, and a setting, `[watchdog] timeout_s` in
`C:\.config\boot.ini` (5 to 600; 0 switches the watchdog off). When saves
move to a background job (item 10) the longest honest stretch drops and the
default can come down.

The watch starts when the loop starts. The start-up screens, mounting the
drive and starting Wi-Fi run before that and are not watched.

### Where the record waits during the restart

| Option | For | Against |
| --- | --- | --- |
| **Memory the restart does not clear** (`RTC_NOINIT_ATTR`, the chip's low-power domain) | Written with plain memory writes: works from the panic handler and from the watchdog, takes microseconds, wears nothing | Lost in a power cut. Whatever is found there at start-up may be rubbish and has to be checked |
| A file on C:, or NVS, written at the moment of the crash | Survives a power cut | Writing flash from a machine in an unknown state, possibly from inside the panic handler or while the stuck task holds the file system's lock |
| ESP-IDF's core dump to a flash partition | The whole state of every task, for a debugger on the PC | A new partition, a flash write from the panic handler, and a PC tool to read it. Nothing the machine itself can show. It can be added later next to this |
| Nothing but the chip's reset reason | Free | "Panic" or "watchdog", never who or where |

Chosen: the no-init memory, 188 bytes. The record carries a magic word, a
version and a checksum; the next start believes it only if all three are
right, copies it out, and wipes it, so a crash is reported once. That start
then writes it to a file in the ordinary way, with the machine healthy. When
there is no record but the chip says the restart was abnormal (a brownout, a
hardware watchdog), that is reported instead, with the chip's reason.

The one-shot fast start (`2026-11-16-one-shot-fast-boot.md`) tried this same
memory and gave it up because the reset after flashing clears it. That is no
loss here: after flashing there is no crash to report.

### What is written down

For both kinds: the program (PID and name, from the process table), the
task, the processor, and how long the machine had been up.

For a crash also: the processor's word for it ("StoreProhibited", "abort()",
"A stack overflow in task ui has been detected."), the address of the
instruction, the address it could not use, and the chain of calls (up to 16
return addresses). The addresses turn into function names on the PC with
`xtensa-esp32s3-elf-addr2line -pfiaC -e build/esp32-os.elf <addresses>`.

For a hang also: how long the task had been silent, and whether it was
running or waiting. **Not where it was stuck.** Getting the address of a task
that is running on the other core means interrupting that core, which is
what ESP-IDF's task watchdog does with machinery of its own. That watchdog is
still on: it prints the spinning core's backtrace on the serial port after 5
and 10 seconds, before ours restarts at 15. So the address is on the wire for
whoever has the cable in, and not in the record. Written under "what is
left".

The process is only named when the task that failed is the UI task. A crash
in the Wi-Fi task says "The task "wifi"", not whatever program the desktop
happened to be calling.

### How to restart after a hang

`esp_restart()` first runs the registered shutdown handlers (Wi-Fi is
stopped politely, among others). Any of them may wait on something the stuck
task holds, and then the watchdog would hang too. The supervisor stops the
scheduler and calls the restart itself (`esp_restart_noos()`), which is what
`esp_restart()` does after its handlers. `abort()` would also restart, but
through the panic handler, with a backtrace of the timer task that means
nothing.

### The error screen

| Option | For | Against |
| --- | --- | --- |
| **A full screen at the next start, before the self-test** | What the review and the owner's choice 11 say: "an error screen". Cannot be missed, also on video. Needs nothing from the desktop, so it still shows if the desktop is what crashes | Holds up the start |
| A message box on the desktop after the start | Lighter | Easy to miss; needs the desktop to come up, which is the thing in doubt; and a new dialog would have to be a program of its own (the rule of 2026-11-17) |
| Both | | Twice the work to say one thing |

Chosen: the full screen. Its details:

- **It goes on by itself after a countdown** (15 s, `[boot] crash_hold_s`; 0
  waits for a key). The board has no keyboard of its own yet: input arrives
  by the debug link or VNC, and VNC is not up this early. A screen that
  waited for a key would leave a bare board stuck on it. A key or a mouse
  button ends it at once, and does not skip the self-test that follows.
- **It shows on a fast start too.** A crash is rarer and worth more than the
  seconds saved.
- **The debug link answers while it shows.** A machine that crashes at every
  start therefore stops at this screen for 15 seconds each time round, and
  can be reached with `tools/dbg.py` in that window. Before, such a machine
  was a blur of restarts.
- **The look is our own**: the self-test's black screen and type, a red
  rule, and the mascot on its back. Not blue, and no borrowed words. The
  pictures are `host/tests/pictures/00d-crash-hang.png` and
  `00e-crash-panic.png`. The owner may well want a different drawing; it is
  one function (`draw_crash_screen` in `core/src/shell/boot.cpp`).
- The self-test's font had no `"` and no `\`. Both were added to it from the
  same Spleen source; the 93 characters it had are unchanged.

### What is kept afterwards

Each report is added to `C:\crash.txt`, which opens in the Editor with a
double click. The file starts again when it would pass 16 KB (about 40
reports). A text file in the root was chosen over somewhere hidden: it is
for the owner to read, and a future `dmesg` can read the same file.

### How to make it fail on purpose

`tools/dbg.py fault hang|pointer|abort [--pid N]`, a new command of the debug
protocol (0x15). The board answers and then fails for real: the UI task spins
for ever, writes through a null pointer, or calls `abort()`. With `--pid`
the fault is charged to that program, as if its code had done it, so the
whole path can be seen with a real program's name. `tools/dbg.py boot crash`
only draws the screen, with this start's report or a made-up one.

Not built: a program in the Start menu whose only job is to crash. It would
make a good scene for the video, but a new program with its own icon is the
owner's call. It is a small thing to add on top of this.

## 4. What was built

- `core/include/core/sys/watchdog.hpp`: `sys::Watchdog`, the heartbeats.
  No clock of its own and no restart, so it runs on the PC. One atomic word
  per watched task.
- `core/include/core/sys/crash.hpp`, `core/src/sys/crash.cpp`: the record
  (`sys::CrashRecord`, a fixed block with no pointers), sealing and checking
  it, the sentence and the detail lines made from it, and the log file.
- `core/src/shell/boot.cpp`: `show_crash_screen` and `draw_crash_screen`;
  `boot_settings` reads the two new settings.
- `firmware/os/main/crash.cpp` and `crash.hpp`: the record's place in no-init
  memory, the supervisor on the timer task, the wrapped panic handler, the
  reset reasons, the faults on purpose.
- `firmware/os/main/main.cpp`: `crash_init()` first thing in `app_main`; the
  report and the screen before the self-test; `watchdog_start` before the
  loop and `watchdog_beat` each time round. `CMakeLists.txt`: the new file
  and `-Wl,--wrap=esp_panic_handler`.
- The debug protocol: `Fault` (0x15), and screen 3 for `Boot screen`.
  `ports::System::fault()`. `tools/dbg.py fault` and `boot crash`.
- `tools/gen_font.py` now escapes `"` and `\` in the list of characters it
  writes (it wrote a string that did not compile once they were in it).
- No change to `sdkconfig.defaults`.

What it costs, from the two firmware builds (this branch and `main`, both
compiled in the cloud with the same tools):

| | `main` | this branch | |
| --- | --- | --- | --- |
| Code and constants (run from external RAM) | 1,232,016 bytes | 1,239,204 bytes | 7,188 more |
| Internal RAM taken at build time (code, data, zeroed data) | 117,771 bytes | 118,087 bytes | 316 more |
| No-init memory in the low-power domain | 0 | 188 | the record |

At run time one timer is created (a few dozen bytes of heap). No task, no
stack.

## 5. How it was tested, and what was not

On the PC (`ctest`, 23 of 23 pass; `crash` is the new one):

- The heartbeats: on time for any length of time; overdue with the right
  silence; a beat that lands just after the supervisor read its clock; the
  millisecond clock wrapping after 49 days; a second watched task; no free
  slot; the setting's limits and "off".
- The record: a sealed one is believed; all zeros, all 0xA5, and every single
  byte of a good record changed in turn (188 cases) are not; nor another
  version, an impossible trace count, a name without its end, or a cleared
  record.
- The words: each sentence and each detail line, for a hang with and without
  a program, a hang in another task, a crash with a trace, and a reset with
  the chip's reason; a buffer that is too small is not overrun.
- The log: made when missing, added to, started again at the limit, an error
  when there is no drive.
- The screen: counts down 15 s and goes on; waits for a slow monitor first;
  a key ends it and leaves the self-test unskipped; with 0 only a key ends
  it; the settings are read from boot.ini.
- The protocol: `Fault` answers before failing, charges the process asked
  for, and refuses a PID that is not running and bad arguments.
- The two pictures are reference pictures: any change to the screen fails the
  picture test.
- The self-test and splash still match the owner's approved drawings pixel
  for pixel after the font gained two characters.

In the cloud, with ESP-IDF v5.5: the firmware compiles and links with no
warnings in the new code. The disassembly shows ESP-IDF's panic code calling
`__wrap_esp_panic_handler`, and the record sits in `.rtc_noinit`.

**Not tested, because it needs the board:** everything that makes this item
what it is. That the record survives the restart. That the supervisor fires
after 15 s and the restart goes through. That a panic's record has the right
program, address and trace. That the screen shows on the monitor and the
countdown runs. That honest long work (a 300 KB save, a screenshot, a VNC
full screen) does not trip it. That the video's late and missed refills and
the Wi-Fi join are as before. The list for the board thread is in the pull
request.

## 6. What was learned

- The review said ESP-IDF's hooks "were not checked". There is no hook, in
  the sense of a function to register. There is one function every panic
  goes through, and replacing it at link time is what ESP-IDF does itself.
- "Hung" is two different things, a loop and a wait, and the cheap watchdogs
  (anything that watches the idle task) see only the first. One line in the
  record tells them apart.
- A crash screen that waits for a key is a trap on a machine with no
  keyboard. The countdown also turned out to be the way back into a machine
  that crashes at every start.
- The no-init memory that was no good for the fast start is right for this,
  for the same reason: it does not survive a reset from outside.
- Writing the record is the easy half. The half that needs care is everything
  that could go wrong while writing it: the record is marked as written
  before the log line is sent, so if logging from the timer task overflowed
  its stack, the panic that followed would not replace the hang's record with
  its own.

## 7. What is left

- The board checks (above). Until then the backlog says "built, PC only".
- **Where a hung program was stuck.** Needs the other core interrupted; or
  the task watchdog's own hook (`esp_task_wdt_isr_user_handler`), which runs
  when ESP-IDF has just collected that backtrace.
- **The start-up is not watched**, nor any task but `ui`. A hang with
  interrupts off is caught by ESP-IDF's interrupt watchdog and arrives as a
  panic. If the timer task itself is stuck, nothing restarts the machine; the
  chip's hardware watchdog could back it up.
- **No date in a report**: the clock is only right once Wi-Fi has set it, and
  the report is written before that. It says how long the machine had been
  up.
- A program that crashes every time it is opened from a start-up file (item
  18) would crash at every start. The screen gives 15 s to get in; a "safe
  start" that skips the start-up file after two crashes in a row belongs to
  item 18.
- Per-process memory limits and heap checks, the review's other "tripwires",
  are not part of this.
- A program in the Start menu that crashes on purpose, if the owner wants
  one for the video.

Found on the way, not from this branch: during the self-test's waits (and
during the error screen) ESP-IDF's own task watchdog prints "Task watchdog

(the task watchdog does not restart the board); the configuration is the same
on main.
