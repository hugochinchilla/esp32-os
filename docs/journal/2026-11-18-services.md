# Services: a dialog, a command, and a stop that sticks

2026-11-18. Backlog item 62 (53 on the branch until main took that number). Built on the branch
`claude/project-thread-wi1e1l`.

## What was asked

The owner, in the project chat:

> Under start -> settings add a Services entry which opens a dialog to
> configure telnet and vnc, simple checkboxes which allow to enable or
> disable the services. The setting is persistent and applies on reboot as
> it just modifies the init config.
>
> Having commands to start and stop the services over tty would be desired
> too, it must not fight the init respawn. If I decide to stop telnet or
> vnc it should not be restarted by init until next boot (if they are
> enabled)

## What was found

The request takes for granted three things that were not so.

- **Telnet and VNC were not in the init config.** `startup.txt` had one
  line for the network, `inetd:once`. Telnet was switched in another file,
  `[telnet] enabled` of `network.ini`, read by inetd's start function. The
  remote screen had no switch at all: it was on whenever inetd was.
- **Nothing of the network could be started twice.** `inetd` is one task
  with one loop (`net::Services`). Its start function opened every port,
  built every service as a static object and started the task; its stop
  (End Task or `kill`, backlog item 5b) ended all of them together and the
  journal of that day says "Starting it again by hand, and the respawn flag
  for services, are not built". `telnetd` could not be ended alone: "its
  port belongs to the same task".
- **init did not respawn any of it.** `inetd:respawn` is answered with
  "inetd cannot be started again when it ends; started once". Only the
  taskbar comes back. So there was nothing for a manual stop to fight
  today; but init had no notion of "stopped by hand" either, and the day a
  service can come back it would have fought.

## The options

**Where the two switches live.**

- *Chosen: two lines of `startup.txt`*, `telnetd:once` and `vncd:once`,
  each a thing init starts. It is what the owner described ("it just
  modifies the init config"), one file says everything that starts, and
  `off` already existed as an action.
- Not chosen: *keep `[telnet] enabled` in `network.ini` and add `[vnc]
  enabled` beside it.* The least code: the dialog would have been an INI
  editor. But it is not the init config, and the file that says what
  starts would go on not saying it.
- Not chosen: *one line with words after it, `inetd:once telnet vnc`.* A
  new field in a format the owner chose to keep at two.

**What a service is to init.** A thing init starts needs a start function;
one that comes back needs a process with its own name, which is how init
knows it ended.

- *Chosen: started and stopped, not respawned.* `telnetd` and `vncd` are
  `Again::No`, like `inetd`. They do not end by themselves (a service of
  the loop has no way to), and `vncd` has no row for init to watch: the
  owner's rule of 2026-11-16 is that only real tasks are listed, and the
  remote screen is not a task. `telnetd` keeps the row it had.
- Not chosen now: *rows for both and `respawn` allowed*, with `kill` on
  the row ending the one service. It would make the respawn real, and it
  needs the owner to say whether a row for `vncd` is wanted after all.
  Left as a question for him.

**How "stopped by hand" is kept from init's respawn.**

- *Chosen: init itself holds it.* `Init::stop(name)` marks the thing held;
  `ended()` and the list of what is due skip a held thing; starting it by
  hand (`start_again`) or a new init (the next start) clears it. It is a
  rule about everything init starts, so it is tested today with things
  that do come back, and `service taskbar stop` works: the taskbar ends
  and stays away, where `kill` on it brings it back.
- Not chosen: *the command edits the file to `off` and back.* Then a stop
  would outlive the next start, which is the opposite of what was asked.
- Not chosen: *a flag in the services loop only.* It would work today,
  because nothing respawns, and would be forgotten the day something does.

**How one service stops while the others run.** The loop's task is the
only one that touches a service and its connections.

- *Chosen: the loop switches it, at its next round.* `Services::want()`
  is called from any task; the loop stops the service (the viewer or the
  session is let go, memory returned), closes its port there, and posts a
  message to the UI task, which removes the row. Starting is the other
  way round: the UI task opens the port, so a port that cannot be had is
  known at once and init's line fails honestly, then tells the loop. On
  the board the loop sleeps at most a second, so a stop takes up to a
  second. `net::Switch` holds the two halves, the same code for the board
  and the simulator.
- Not chosen: *end inetd and start it again without the service.* The
  other service's viewer or session would be dropped, and the task and its
  static objects were not written to start twice.
- Between a stop and the loop's answer a start is refused ("it is still
  stopping; try again in a moment") rather than queued: the port is not
  the UI task's to open until the loop has closed it.

**The command.** `service NAME start|stop|status`, and `service` alone
for the list. Chosen for the Unix name, as the shell's other commands;
`net start telnetd` (DOS, NT) is the other tradition and can be added as
another name if the owner wants it. `telnet` and `vnc` are accepted for
`telnetd` and `vncd`.

## What was built

- `core/init`: `set_stop`, `stop` (with `Stopped`), `down`, `info`; the
  held mark. `line_action` and `set_line_action`, which read and change
  one line of the file's text in place: the first line for a name is
  changed where it stands, later ones for it go, none means one is added
  at the end, and a result that does not fit changes nothing. The usual
  file has `telnetd:once` and `vncd:once`. Room for 12 things, from 8.
- `core/net/services`: a service can join the loop switched off; `want()`
  and `on()`; services are added while the loop runs.
  `core/net/switch`: `net::Switch`, start and stop of one service with its
  port and its row. `WebGate::hang_up()`, because the web port's
  connections are handed out again after a stop and start.
- `core/src/shell/services.cpp`: the Services dialog, a program of its
  own on the OS calls (21 of 21 programs moved). Two check boxes, "No
  passwords: for a network you trust.", "Changes apply the next time the
  machine starts." Only a box that was changed changes its line. Without a
  file it starts from the usual text, which is what init went by. Its
  entry in Start > Settings, and a 16x16 icon (two rack units, one light
  green and one red; original).
- `core/src/sh/system.cpp`: the `service` command.
- The board (`firmware/os/main/main.cpp`), the simulator (`host/sim.cpp`):
  `inetd` starts the task and the update service only; `vncd` and
  `telnetd` are added to init with their stop functions. `inetd` starts
  whenever there is a radio, also with nothing to listen on. mDNS
  (`wifi_announce`) can be called again: `chinchilla.local` is announced
  by inetd, the `_rfb` and `_http` services by vncd, and taken back when it
  stops. When inetd is ended, init is told its two services are down.
  The desktop program and the browser build have a `telnetd` and a `vncd`
  that serve nothing, as their inetd does.
- `[telnet] enabled` in `network.ini` is not read any more.

## What was learned

- The owner's picture of the system was ahead of the system: he asked for
  a dialog over a config that did not hold these settings, and a stop that
  would not fight a respawn that did not exist. Most of the work was
  making the system match the picture.
- A stop has to be closed on the task that owns the socket, and a start
  wants its answer at once. The two halves on two tasks, with a refusal
  in between, came out simpler than a queue of wishes.
- The web gate kept pointers to connections of its port. Nobody had
  stopped and started that port before, so nobody had seen that the port
  would hand the same objects out again.

## What is left

- **The board's `startup.txt` has no `telnetd` or `vncd` line**, so after
  this change neither starts there until the file is deleted (init writes
  the usual one) or Services is opened and both boxes ticked. No backward
  compatibility, by the owner's rule; the board turn does it.
- On the board: both services from the file; `service vncd stop` with a
  viewer connected (the viewer drops, about 184 KB of external RAM
  returns, ports 5900 and 80 refuse, telnet goes on working); `service
  telnetd stop` typed in a telnet session (it hangs up on itself);
  start again; the dialog's change surviving a restart; mDNS after a stop
  and a start; `dbg.py misses`.
- For the owner to say: the names `telnetd` and `vncd`; whether no line
  should mean not started; whether the services should get rows and
  `respawn`; whether updates belong in the dialog too.

## On the board, first turn: inetd would not start twice (2026-11-18)

The board thread ran commit e28f65d with main merged in. The usual file,
`service` stop and start of vncd and telnetd, the dialog's `off` and `once`
and the taskbar's stop and start all passed. One thing failed, outside the
list of checks and rightly tried: after `kill` on inetd, `service inetd
start` logged "init: started inetd", then two errors from mDNS
(`mdns_service_remove_for_host: Invalid state or arguments`) and "network
services (inetd) ended: the ports are closed". After that `service telnetd
start` did not start, and only a restart of the machine brought the
network back. Not merged.

**Why.** This branch tells init that inetd is down when its loop has
ended, so that its services could say "inetd is not running". That made
inetd something `service` could start again, and its start function had
never been written for a second time: the loop still had its stop flag
set, so the new task's first round answered "stopped" and the task ended.
Before this branch nobody could ask for a second start at all. The PC
tests had the same hole: they checked that telnetd would not start after
the kill, and stopped there.

**The options.**

- *Chosen: inetd starts again.* `Services::restart()` makes a loop that
  has ended new: every service is as it was when it joined (updates on,
  the two switched ones off until started). The start function refuses
  while the old task has not yet said it is done, adds the update service
  to the loop only the first time, and `service inetd stop` now works too
  (it is End Task by another name, and init holds it). The services inside
  are not started with it: the file is read once, at the start of the
  machine, and what runs after that is what was asked for by hand.
- Not chosen: *refuse the second start with a clear message.* Less code,
  and it would leave "only a restart brings the network back" as it was.
- Not chosen: *inetd's start also starts what the file says.* init would
  have to read the file again for three lines; left for when it is wanted.

**Also.** mDNS logged an error for each service taken back that had not
been announced; `wifi_announce` now remembers what it announced. `kill
inetd` is refused because `kill` takes numbers, as on Unix; names were not
asked for.

**The memory note.** After one stop and start of vncd the largest free
block of internal RAM was 116,736 bytes where it had been 129,024, and it
stayed there.
Nothing in our code keeps internal memory across that cycle (the viewer's
buffers are external), so the first suspect is the network stack's own
listening sockets and mDNS records landing in a different place than the
ones they replaced. One cycle cannot tell a leak from a block that moved:
the next turn repeats the cycle five times and reads the total free and
the largest block each time.

**Tested.** `test_services`: a loop run a second time, each service as it
joined, and a switch started on it. `tools/test_serial_console.py` on the
simulator: `service inetd stop`, the ports close and the rows go, telnetd
refuses, `service inetd start`, `service telnetd start`, telnet answers;
the same after `kill` on inetd, which is the board's failing case. The
firmware compiles; this second version has not run on the board.
